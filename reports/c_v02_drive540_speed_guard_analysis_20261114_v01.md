# 0.03 m/s 속도 가드 분석과 운영 개선안 — 2026-11-14 v01

이번 작업은 CPU 분석만 했습니다. 기존 코드, 결과, 본실험(HOLD 상태)은 바꾸지 않았고, 새 주행이나 재개도 하지 않았습니다.

## 결론
- **0.03 m/s는 명령 속도의 상한이 아닙니다.** 측정 속도에 대한 안전 기준으로 세 군데에서 쓰입니다(1절).
  - 실제 주행 명령은 **0.02 m/s로 순항**합니다(`construction_site_follower_v19`: `v=min(.02, …)`).
- **11회차 HOLD는 실제 과속이 아니었습니다.** 단 1틱(1/60초)의 측정 튐이었습니다.
  - 지금까지 기록된 주행 89회(이전 Stage-4 포함)에서 0.03 이상이 나온 틱은 단 2개였고, 둘 다 단독 1틱 튐이었습니다.
  - 0.1초 평균 속도의 최댓값은 0.0267로, 0.03을 넘은 적이 없습니다.
- **개선안(A+B)을 쓰면 불필요한 HOLD는 사라집니다. 실제 주행 시간은 줄지 않습니다.**
  - 명령 속도 0.02 m/s와 감속·정지 규칙을 그대로 두기 때문입니다. 1회 약 305초, 540회 약 27–35시간 예상은 그대로입니다.
  - 주행 시간을 줄이려면 명령 속도를 올려야 하는데, 이는 프로토콜 변경이고 측정 튐도 커집니다. 권장하지 않습니다.

## 1. 0.03 m/s가 쓰이는 곳 (코드)

| 위치 | 역할 | 입력 | 결과 |
|---|---|---|---|
| ① 드라이버 속도 governor (`fe2e_v02_speed_governor_v03`, PRE_FINAL 단계 `ceiling=.03`) | **명령 측 보호** | 측정 속도(틱마다) | 측정 속도가 ceiling−0.003 이상으로 예측되면 감속 명령, 0.03 이상이면 그 순간 명령을 0으로. 실행은 계속 |
| ② 세션 안전 가드 (`session v04` 310행: `phase=='pulse' and speed>=.03`) | **실행 중단 기준** | 그 틱의 base 평면속도(root velocity에서 계산) | `abort_motion` → 드라이버 종료 → `LEGS_INCOMPLETE` |
| ③ 결과 판정 (`stage4_ablation_outcome`: `SPEED_GUARD=.03`) | **결과 기준** | 주행 중 한 틱이라도 0.03 이상 | `speed_guard_trip=True` → SUCCESS가 될 수 없음 |

- **명령값 자체:** follower가 0.004–0.02 m/s를 요청합니다. governor의 기준 상한은 0.022이고, 바퀴 명령 상한은 0.05(바퀴 표면 속도)입니다. 11회차의 명령(wire_v 0.004–0.005 = 표면 속도 약 0.02 m/s)은 평소와 같았습니다.
- **11회차가 HOLD된 경로:** ② 실행 중단 → 드라이버 종료 → `LEGS_INCOMPLETE` 예외 발생. 이 예외는 "영점 복구 대상 고장" 목록(`eligible_fault`)에 없습니다. 그래서 `FAULT_NOT_SAFE_FOR_ZERO_RECOVERY`로 정지 인증을 하지 않았고, 기술 판정 실패로 HOLD됐습니다.

## 2. 순간 튐과 실제 과속 구분 (실측, 주행 89회)

분석 대상은 지금까지의 모든 주행 기록입니다(이전 Stage-4 pilot/run01/run02, 벤치마크, 재검증, 파일럿, 본실험 5회). 결과 파일은 `sdg_final/C_V02_SPEED_GUARD_ANALYSIS_20261114_v02/`에 있습니다.

| 지표 | 값 |
|---|---|
| 틱 단위 최댓값 | 0.03057 (Stage-4 run02 HR, 최적화 전), 0.03044 (본실험 11회차) |
| 0.03 이상이었던 틱 | **89회 주행 전체에서 2틱**. 둘 다 1틱만 넘고 바로 내려옴 |
| 0.025 이상이 연속된 최장 구간 | 5틱 (0.083초) |
| 0.1초(6틱) 이동평균 최댓값 | **0.0267** (기준 0.03 대비 여유 11%) |
| 0.25초(15틱) 이동평균 최댓값 | 0.0246 |

- 명령이 0.02 m/s로 일정할 때도, 측정 속도는 틱마다 약 0.012–0.030 사이에서 출렁입니다. 바퀴와 스캔 바닥 사이 접촉의 영향입니다.
- **결론:** 지금까지의 모든 기록에 지속적인 과속은 없었습니다. 0.03 초과는 모두 단일 틱 튐이었습니다. 최적화 전 코드(Stage-4, B0)에서도 같은 현상이 있었습니다.

## 3. 개선안 A: 단일 틱 튐에 강한 가드 (실제 과속 감지 능력 유지 검증)

**새 실행 중단 기준 F** (② 실행 중단 기준과 ③ 결과 기준에 같이 적용. ① governor는 그대로)
- (a) 한 틱이라도 0.045 m/s 이상이면 즉시 중단 (0.03 × 1.5, 급격한 폭주 대비)
- (b) 0.1초(6틱) 이동평균이 0.03 m/s 이상이면 중단

**검증 1: 오탐** (주행 89회)

| 가드 | 실제 주행에서 작동한 횟수 |
|---|---|
| 현행 R | 2회 (모두 단일 틱 튐) |
| 개선안 F | **0회** |

**검증 2: 실제 과속 감지** (89회 기록에 지속 과속을 인위적으로 주입)
- 측정 노이즈는 그대로 두고, 주행의 5개 시점부터 평균 속도를 L로 올렸습니다. 조건마다 445개 사례입니다.

| 지속 과속 L (m/s) | R 감지율 / 최대 지연 | **F 감지율 / 최대 지연** | F 지연 중 추가 이동 |
|---|---|---|---|
| 0.031 | 100% / 4틱 | **100% / 10틱 (0.167초)** | 최대 5.2 mm |
| 0.033 | 100% / 1틱 | 100% / 5틱 (0.083초) | 2.8 mm |
| 0.036 | 100% / 1틱 | 100% / 5틱 | 3.0 mm |
| 0.040 | 100% / 0틱 | 100% / 5틱 | 3.3 mm |
| 0.060 | 100% / 0틱 | **100% / 0틱** (즉시) | 0 |
| 0.200 | 100% / 0틱 | 100% / 0틱 | 0 |

- 지속 과속은 F도 100% 감지합니다. 늦어지는 시간은 최대 0.167초, 그동안 더 가는 거리는 최대 약 5 mm입니다.
- 0.045를 넘는 큰 과속은 현행과 같이 즉시 감지합니다.
- ① governor의 틱 단위 명령 차단, 비상 범위 가드(속도 0.25 m/s 또는 3.2 m 이탈 시 정지), 경로 추종 가드, 충돌 검사는 모두 그대로입니다.
- **한계:** 이 검증은 기록된 노이즈에 과속을 덧씌운 모의 시험입니다. 실제 시뮬레이션에서 과속을 일으켜 본 것은 아닙니다. 처음 설계에 넣었던 이동거리 기반 기준(c)은 계산 결함으로 결과가 무효라서 제안에서 뺐습니다.

## 4. 개선안 B: 가드가 작동한 실행은 정지를 독립 검증한 뒤 실패로 기록하고 계속

- 기존 세션에는 이미 **고장 후 영점 복구 절차**가 있습니다. 경로 추종 이탈, 목표 초과 같은 고장에 쓰고 있습니다. 순서는 다음과 같습니다.
  1. 드라이버가 정상 종료했는지 확인
  2. ROS 관측기로 0 명령 수신 영수증(receipt) 확인
  3. 그래프의 바퀴 명령을 0으로 설정하고, 실제로 0인지 확인
  4. 물리 시뮬레이션을 다시 돌리며 정지 상태(속도 0.002 m/s 미만, 1초간 이동 2 mm 미만) 확인
- 개선안은 F 가드가 작동한 경우에도 이 절차를 실행하는 것입니다.
  - 모두 통과하면 `FAIL_SAFETY_ABORT`(정지 검증됨)로 기록하고 Controller가 다음 시도로 넘어갑니다.
  - 하나라도 실패하거나, 충돌·외피 침범이 있거나, 다른 기술 문제가 겹치면 지금처럼 **HOLD**합니다.
- 필요한 변경 (모두 새 버전으로 만들고, 기존 파일은 보존)
  - session v05: F 가드 적용, 가드 작동 시 `SPEED_GUARD_ABORT` 예외 발생, 영점 복구 대상에 추가
  - 결과 판정과 기술 gate의 새 버전: F 기준 적용, "정지 검증된 가드 정지"를 정상적인 과학적 실패로 인정
  - Controller v06
  - 개정안 v04, 실행 잠금 갱신, 재승인

## 5. 가드 제거 검토 (권장하지 않음)
- 가드를 제거하면 ① governor가 틱마다 명령을 차단하는 것만 남습니다. 0.03–0.25 m/s 사이의 중간 수준 과속은 실행이 중단되지 않습니다(비상 범위 기준은 0.25 m/s).
- 따라서 **같은 수준의 안전이 보장되지 않습니다.** F처럼 가드를 유지하면서 단일 틱 튐만 걸러내는 방식을 권장합니다.

## 6. 기존 11회 결과에 대한 영향
- **1–10회:** F 기준을 적용해도 결과가 같습니다. 최댓값이 0.0293으로 두 조건 모두에 걸리지 않습니다.
- **11회:** F 기준이었다면 가드가 작동하지 않았을 것입니다(0.1초 평균은 0.03 미만). 다만 실제로는 현행 규칙으로 중단됐습니다.
- **권장:** 개정 프로토콜(v04)로 **540회를 처음부터 새 출력 폴더에서 시작**합니다.
  - 앞의 11회는 "개정 전 첫 시도(중단)"로 보존하고 공개하며, 본실험 결과에는 넣지 않습니다.
  - 잃는 시간은 약 30분이고, 한 실험 안에 두 가지 판정 규칙이 섞이지 않습니다.
- **대안:** 1–10회는 유지하고, 11회만 v04로 다시 실행합니다. 이 경우 같은 시도를 두 번 실행한 셈이 되므로 공개해야 합니다.

## 7. 시간 영향
- **주행 시간은 줄지 않습니다.** 명령 속도(0.02 m/s 순항), 감속, 정지 인증이 그대로입니다. 1회 약 305초, 540회 약 27–35시간입니다.
- **줄어드는 것은 HOLD와 중단으로 잃는 시간입니다.** 지금 규칙으로는 E1 경로에서 주행 6회 중 1회가 HOLD됐고, 그때마다 사람의 조치가 필요했습니다.
- **추가로 드는 시간:** 가드가 작동한 실행은 영점 복구를 하느라 수 초가 더 걸립니다(최대 20초 대기).
